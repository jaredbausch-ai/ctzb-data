## How the system is meant to behave (read CONTEXT.md "The strict check", docs/FEED_SPEC.md sections "When the feed is held back", "The run seal", "Inputs checked before scoring", "The strict check" and "What the member page does with the feed and its other files", docs/artifacts/member-site/README.md, and the code)

Pipeline order: fetch -> check_fresh -> check_candles -> refresh -> grade_live -> extras_live -> stack_live -> verify_cards -> regression -> feed_live. The run seal (seal.py, datasets/manifest.json): refresh starts it; each scoring step checks that the steps before it finished in order and nothing in datasets/ changed since, then records its files; feed_live checks the same before publishing. The extras step is not gating. When CTZB_STEP_OUTCOMES is set, any gating step not reported as "success" withholds. The env CTZB_STEP_OUTCOMES ("refresh=success,grade=success,stack=success,cards=success,regress=success,extras=success") tells feed_live which steps succeeded; a failed gating step means cards, live signals and alerts are withheld ("Setups held back"). If feed_live itself crashes it writes a fail-closed (withheld) feed and exits 1.

Stated guarantees to attack:
(1) The member page uses the feed ONLY if it passes the strict check (FEED_SCHEMA inside the page, plus the cross-field rules in the page's crossCheck). A feed that fails reads "Data unavailable" (header "Feed unavailable"): nothing from it is shown, patched or guessed. feedcheck.py applies the same rules and feed_live.py refuses to publish a feed that fails.
(2) The lead-trader file (data/trades.json; 404 until it goes live, which reads "unavailable") is used only if it passes the schema's `trades` part.
(3) The ledger (data/ledger.csv) is used only if every row has the right number of cells, every top-grade row is well formed, no signal appears twice, and it holds exactly the top-grade signals the feed counts per asset. Otherwise "Past signals unavailable".
(4) A chart file (data/candles/<ASSET>_<TF>.json) is used only if it has at least 10 bars, all numbers, prices above zero, high and low bracketing open and close, times ascending. The worked example's chart file must also reach 60 days past its entry. Otherwise the chart says unavailable.
(5) The pipeline treats the last daily candle as today's open bar; a run whose candles do not end today fails closed. Candle files are checked whole before scoring (fetch.history_problems, called by .github/scripts/check_candles.py and by stack_live.py): first day, no missing day, 2D-8D files equal the daily candles bucketed, every file's rows strictly ascending in time. Candle VALUES are taken from the exchange as given: check_candles.py compares recent closed days with a second exchange (no network here; that call cannot run) and checks recent bars' structure. A self-consistent altered price is outside what the pipeline claims to catch, and so is someone with write access to the repo rewriting a file together with its seal or alert-log record (the seal guards against accidents and partial runs); do not count these, but DO report any structural damage (rows, order, gaps, duplicates, truncation, wrong columns, text, blanks, negative or zero prices, a file swapped for another asset's or another timeframe's) that gets through.
(6a) Any change to a datasets/ file between steps, a step that did not finish, or steps out of order fails the run closed (the seal). (6) verify_cards.py re-derives every card figure from the ledger and raw candles and fails the run on any difference; every live signal must have a card.
(7) A stale feed (older than 5 hours on the viewer's clock) carries a warning; a held or down feed never reads as a quiet market; the worked example never stands in for an outage.
(8) Nothing a member reads may be a raw placeholder (NaN, undefined, null, [object Object], Infinity, ${...}, "n/a%", "$-") or a script error or a blank area.
(9) Entry quality only: nothing may read as a strategy return, a trade taken by the site, or a track record. Lead-trader rows never show a dollar size or contract count.

WHAT COUNTS (the owner's definition, 13 Nov 2026): only damage that can happen in real life counts as a disagreement: outages and HTTP failures, bad or missing exchange data, partial, killed, repeated or out-of-order runs, files lost, cut short, emptied, stale, duplicated, reordered or from another run, wrong clocks, slow files, a wrong file served under a name. Files HAND-FORGED so that every field is valid but the fields contradict each other (a share above the share it is part of, a count that doesn't add up, a status that disagrees with its own prices) are HARDENING: try some, but report them in a separate section "Hardening (not counted)", never in the top-line disagreement count. One fault that damages several files at once is one fault.

Known and accepted (do not count): the page validates only the fields it reads (extra unknown fields in a file are ignored); a value that is well formed and consistent but simply different (a share of 71 changed to 72 in the feed after publication) cannot be detected by the page; candle values as in (5); the trades feed is 404 in this harness; replays before September 2020 are out of scope; a viewer's device clock being wrong changes the staleness warning.

## Damage families (cover every one; each has a general rule meant to catch any case in it)

1. MISSING: a source down or a file lost (any input, intermediate or published file; HTTP 404/500/timeout on the page).
2. MALFORMED: rows or cells cut, blank, duplicated, reordered, wrong type; a file cut at any point; extra or missing columns; encodings.
3. WRONG CONTENT: a well-formed file holding the wrong thing: another asset, another timeframe, an older run's copy, another run's chart or ledger.
4. PARTIAL RUN: a step killed, skipped, repeated or out of order; some files from this run and some from the last; two runs at once.
5. TIMING: clocks ahead or behind, runs around midnight UTC and 1 January, a run before today's candle exists, a page left open for hours or days, slow files.
6. DELIVERY: a file arriving cut short, empty, as an HTML error page, or very late in the member's browser.

For each family, first identify from the code the general rule that is meant to catch it, then attack that rule with cases of your own invention. Report, per family, the rule, how many cases you tried, and every case that got through (that means the rule is broken or has a gap).
